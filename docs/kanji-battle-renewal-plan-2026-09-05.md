# 漢字対戦の不具合調査・刷新案

調査日: 2026-09-05。対象: ローカル HEAD `4cc1eaf`、`/yamato/battle`。実装・デプロイは未実施。

## 1. 調査結果と確度

### ① 待機が25秒になり、回答時間が0秒になる

本来の設定は回答30秒、問題間カウントダウン3秒、次問開始前バッファ1秒。初問はプレイ画面の準備完了後に3秒のバッファがある。25秒という待機設定はない。

確認した原因候補・欠陥:

- `src/app/yamato/battle/room/[roomId]/play/page.tsx:185`〜190、283、293、313: 進行役の `Date.now()` で開始時刻を保存し、各参加者が自分の `Date.now()` で比較している。サーバー時刻との差分補正がない。進行役は必ずしもホストではなく、離脱していない参加者キーの先頭（183行付近）。時計差のある別端末へ進行役が変わっても影響する。
- 進行役の時計が参加者より24秒進んでいる場合、次問の「開始前1秒」が参加者には「スタート25秒」になる。ローカルで現行の式を使い確認した。
- 同ファイル491行以降: 問題・入力欄を隠す条件は主に `loading`。`inBuffer` と `countdown` でも問題・手書き欄が表示される。
- 561行以降: `HandwritingCanvas` に既存の `readOnly` を渡していない。開始前・問題間・送信後も描画できる。戻す／クリアも開始前を制限していない。
- 218行以降: `writeAnswer()` 自体は開始前チェックを持たず、`answering` と `countdown` の両方を許可する。負の経過時間は `clampResponseMs()` で0に変換される。`countdown` に入ると未回答者は自動送信するため、ボタン以外の経路にも対応が必要。
- `database.rules.json:35`〜39: 回答の開始時刻、現在の問題番号、時間範囲、初回のみという検証がない。
- `functions/src/index.ts:1060`: 採点時にRTDBの `responseMs` を読むが、その値自体がクライアントの直接書き込み。0秒を正しい回答時間としてスコア・合計時間へ反映し得る。

**確度の限界:** 時計差による25秒表示、負の時間の0秒化、待機中の問題表示・入力可能はコードと計算で確認。現行の送信ボタンは613行で `inBuffer` 中は無効化され、25秒後に送信する予約処理も見つからない。そのため報告された操作全体の原因確定には至っていない。実際の表示が「スタート25」「次へ3」「残り25」のどれか、稼働版との一致、端末時計差、通信切断・再接続、フェーズ受信順を再現テストで確認する。通信待ちを時計差と断定しない。

修正案:

1. 開始・締切・問題間の時刻をサーバーで決定する。画面表示はRTDBの `.info/serverTimeOffset` を用いた補正時刻で統一する。時計同期前・接続断中は入力可能にしない。補正値は表示用であり採点の信頼根拠にしない。
2. 初問準備 → 開始カウントダウン3秒 → 回答30秒 → 問題間3秒 → 次問、と状態を明確化する。次問の追加1秒は廃止して問題間3秒に統合する案を推奨。全員回答済みなら30秒を待たず問題間へ進む。
3. 開始前・問題間には問題文、問題画像、手書き欄を表示しない。回答中でも送信済み・送信中・期限切れは `readOnly` と共通の入力許可条件で停止する。ボタンだけでなく送信関数内でも再検証する。
4. 期限到達時に手書き画像を一度だけ確保してから待機表示へ移る。現在は画面上のキャンバスから自動送信用画像を取得しているため、先にアンマウントすると画像が失われる。画像・筆跡は問題IDごとに保持し、次問のクリアや遅れて返る送信結果が別問題へ混ざらないようにする。
5. 回答確定は `submitKanjiBattleAnswer`（仮称）へ移す。認証・漢字利用権・在室・非離脱・対戦ID・問題番号・受付期間を検証し、サーバー受信時刻から回答時間を決定する。開始前は拒否し、負値を0へ補正して受理しない。同じ問題の再送は初回の結果を返し、時間を上書きしない。
6. 時間切れは回答時間30秒として別経路で一度だけ記録。締切直前に送った通信の到着猶予を設ける場合は小さな固定値にし、締切後受信は30秒扱いにする。受信基準では通信遅延も回答時間に含まれることを仕様化する。
7. 問題ごとの `startsAtMs / deadlineAtMs / closesAtMs` を保存し、OCR採点はサーバー確定回答だけを読む。未回答・期限切れの画像の扱いも揃え、回答記録のない画像で速度加点しない。
8. 進行更新をサーバーのトランザクションへ移し、対戦ID・問題番号・状態バージョンが一致する場合のみ遷移する。クライアントは締切時に進行確認を依頼できるが、状態を直接決定しない。タイムアウト回収用の遅延ジョブも同じ検証を通す。ジョブが遅延しても締切以降の入力は許可しない。

### ② 5名以上が入室する

原因はコード上で確認できる。

- `src/app/yamato/battle/page.tsx:305`〜327: `get()` → 人数チェック → 自分の参加者ノードへ `set()` と分かれている。3人のルームへ2人が同時参加すると両者が「3人」と読んで成功し、5人になる。現行条件を再現するローカル計算で確認。
- 316行: `!participants[user.uid]` の場合だけ満員チェックする。`abandoned: true` の参加者記録が残っていると、他の4人が在室していても、そのユーザーの復帰を許可する。こちらも現行条件で確認。
- `database.rules.json:29`〜31: 自分の参加者レコードは `waiting` または `active` なら書ける。人数制限がなく、直接URLの待機画面の準備操作／プレイ画面の準備更新でも会員追加を防げない。
- ルーム直下のホスト向け包括書き込み権限も強すぎる。子の `.write: false` だけでは親の許可を取り消せない。
- 待機画面 `startBattle()`（137行以降）は最低2人のみ検査し、4人上限がない。開始カウントダウン中も `status: waiting` のため入室可能。終了時に人数・準備状態を再確認せず `active` にしている。
- 待機画面の「戻る」はページ移動のみで明示退出しない。ページ離脱時に `onDisconnect` を解除するため、接続が続くと在室情報が残り得る。

修正案:

1. `joinKanjiBattleRoom` に入口を統一し、Admin SDKのルーム単位トランザクション内で「募集状態・未期限切れ・開始前・空席・既存在室」を確認して参加を確定する。人数上限はサーバー固定4人。
2. 現役メンバーの重複参加は人数を増やさない冪等操作。退出済みユーザーの復帰は新規入室と同じ空席検査を行う。
3. 開始・参加・退出が同じルーム上で競合するようにする。開始時は2〜4人、全員準備済み、問題取得済みを再検証し、募集を同時に閉じる。
4. クライアントからのメンバー作成・復活、定員・状態・回答・結果の変更を禁止する。親の包括書き込み許可を除去してから必要最小限の権限を定義する。本人の接続情報は別パスに分ける。
5. 待機中の明示退出は `leaveKanjiBattleRoom`。ホスト退出はルーム解散を推奨。参加者退出は空席へ戻す。開始前カウントダウン中の退出は開始を中止し再準備させる。
6. ネット切断は接続ID単位のpresenceと短い猶予（案:15秒）で処理。猶予中は席を予約し、失効後にサーバーが退出確定する。同一UIDの複数タブの片方を閉じただけで退室させない。

## 2. 新しいマッチング方式

### ユーザー操作

対戦トップの主導線を「ルームを作る」「ルームに参加する」の2択にする。

| 選択 | 画面・操作 |
| --- | --- |
| ルームを作る | 出題単元を選択 → 作成 → 自分がホストの待機室へ |
| ルームに参加する | 募集中ルーム一覧 → ルームを選択 → 入室確定 → 待機室へ |

一覧カードはホスト表示名、単元名、現在人数（例:2/4人）、参加ボタンを表示。新しい順に並べ、満員・開始済み・期限切れ・解散済みは除外する。誰もいないときは「参加できるルームはありません」と作成への導線を出す。自分の在室ルームは「戻る」として別表示する。

一覧を開いている間だけリアルタイム購読。取得中、取得失敗、再読み込み、参加処理中を区別する。表示後に満員になった場合はその旨を表示して一覧を更新し、別ルームへ勝手に参加させない。

現行の「おまかせで参加」、ルーム番号入力参加、作成側のランダム範囲カードを撤去する案。内部のルームID・既存結果URLは維持できる。ランキングとプロフィールは付帯表示として継続する。

### サーバーとデータ

- 新規 `functions/src/kanjiBattle.ts` に作成・参加・退出・準備・開始・進行・回答確定処理を集約し、`index.ts` から公開する。既存のOCR・結果確定は呼び出し契約を合わせて利用する。
- 現行 `kanjiBattleRooms/{roomId}` を正本とし、`schemaVersion: 2`、対戦識別子、メンバー、定員、状態バージョン、サーバー時刻を持つ。既存の `unitId` 等は問題取得との互換を維持する。
- `kanjiBattleRoomListings/{roomId}` を公開一覧用の要約として用意する。ホスト表示名・単元名・人数・作成時刻・有効期限・バージョンだけを公開し、回答や参加者全員の情報を配信しない。表示名未設定時にメールアドレスを使わない。
- 一覧は正本の更新からサーバーが投影する。イベント順序の逆転・再配信を考慮して古いバージョンで戻さない。定期修復で期限切れ要約を削除する。一覧の遅延があっても入室時は必ず正本で再検証する。
- 一覧は作成時刻のインデックス・ページングで取得する。現行の `status=waiting` 先頭30件を取得した後にクライアントで空席判定する方式は、古い無効ルームが30件を占めると新しい部屋を見逃すため引き継がない。
- 認証、アプリ利用権、漢字利用権を各Functionで検証する。ルーム本体は在室者と管理者が参照でき、一覧は利用権を持つユーザーが読める設計とする。現在はルーム集合の親で読み取り許可しているため、親の権限も変更する必要がある。
- 作成は一意IDを使い、リクエストIDによる冪等化を行う。現行の「6桁番号の存在確認後にset」は引き継がない。参加もリトライで席が増えないようにする。
- presenceを管理するフックを待機／対戦ページ共通の親へ置き、ページ遷移時の切断監視解除漏れを防ぐ。手書き画像は既存の一括OCR方式を基本とし、問題ごとの確定回答と対応させる。

## 3. 実装・検証の順序

1. 既存バグの再現ケースを固定し、時刻と状態の仕様を確定する。
2. 参加・開始・退出をトランザクション化し、直接書き込み経路を閉じる。
3. サーバー時刻・回答確定と待機画面を実装する。
4. 一覧投影と2択画面を実装し、旧マッチング処理を削除する。
5. Emulatorでルール・Functionsを検証し、複数ブラウザで対戦完了・OCR・順位まで確認する。

必須ケース:

- 端末時計±24秒・±60秒、進行役の切断、画面バックグラウンド復帰でも問題間待機と回答時間が崩れない。
- 開始前・問題間・期限後に問題が見えず入力できない。開始前API送信が拒否される。
- 締切直前の送信、未送信の自動確定、フェーズ遷移と通信応答の順序逆転、二重クリックで画像・時間が別問題へ混ざらない。
- 3人から2人同時参加は1人だけ成功。4人の部屋へ退出済みユーザーが復帰できない。同一ユーザーの重複参加は1席。
- 入室と開始・退出・解散が同時でも定員と準備条件を維持。URL直アクセス・直接DB書き込みでも追加参加できない。
- 画面の「戻る」、タブ終了、ネット切断、再接続、複数タブで在室人数と一覧が復旧する。
- 一覧表示後の満員化、期限切れ、要約更新の逆転、30件以上のルーム、作成リトライを検証する。
- 10問の画像がOCRへ渡り、サーバー確定時間だけが速度点・順位に使われる。

現在の `npm run test:security` はFirestoreだけを起動するため、今回必要なRTDBルール検証の代わりにはならない。Database Emulatorを使う専用テストと実行経路を追加する。Functions型チェック、フロントのビルド、文字化けチェックも実施する。

旧画面はDB直接書き込みに依存するため、新ルールと混在させない。切替は新規作成を一時停止し、進行中対戦を終了させてからFunctions・ルール・フロントを揃える。旧画面へは更新案内を表示する。既存結果は保持する。新規問題キャッシュは対戦識別子／スキーマ版を含め、旧キャッシュを誤利用しない。

## 4. 今回の検証範囲

ソース、RTDBルール、既存テスト構成を確認。現行計算式の小さなNode検証で、24秒の時計差→25秒表示、開始前経過時間→0秒、同時入室→5人、退出済み参加者の満員チェック回避を確認した。実ブラウザで報告操作全体の再現、本番ログ・デプロイ版の照合、修正後テストは未実施。変更はこの計画書のみ。

Firebaseとsecurity-auditのスキルに基づき、UI変更に加えてサーバーのトランザクションと親階層の権限制御を設計に含めた。
